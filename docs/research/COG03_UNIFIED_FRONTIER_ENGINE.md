# COG-03 — Unified frontier HDC engine: owner direction, 2026-11-17

The research objective is a coherent and optimized hyperdimensional computing architecture, informed by the latest research and designed together with hardware execution, rather than a collection of independent paper demonstrations or third-party adapters. Preserve all 85 registered research targets, evaluate them rigorously, and incorporate scientifically useful compatible mechanisms into a shared typed execution engine. Negative comparisons with deterministic software are valid findings, not a reason to abandon research. No guaranteed speedup, blanket HDC superiority, or predetermined production deployment. Owner wishes to discover useful HDC workloads beyond low-resource/low-power niches. CPU remains the portable reference and default; accelerator suitability is a research hypothesis. No hardware purchase authorized by this note.

## Architecture direction

One shared representation/operation contract, one execution planner with bounded admission/cancellation, one reference verification boundary and one reproducible comparison framework. Representations may have incompatible algebra and must carry typed shape, precision, normalization, tie, inverse, codebook, layout, and provenance metadata. Never reinterpret FHRR as MAP or flatten noncommutative binding into a coordinate-wise product. Compose compatible learned encodings, structured binding, bundling, memory, cleanup/factorization, calibrated abstention and verification in actual task pipelines rather than claiming benefit from independent microbenchmarks. Research methods are candidates for shared implementation, not plug-ins merely placed alongside each other, and not obligatorily chained into every query. Keep optional backends within one engine, not second execution/memory authority. SQLite/ANSF continues as canonical host store; HDC approximates and proposes; deterministic verification of factual claims is unchanged.

FHRR is the owner's preferred initial general-purpose compositional representation hypothesis; verify actual task and total cost rather than mandate universal FHRR. Packed BSC/MAP are important low-precision candidates; other algebras remain tested. GHRR is an optional specialist/fallback where order-aware noncommutativity or structural capacity yields demonstrable benefit, not an automatic route after failed exact search. Compare FHRR with role/position permutations to GHRR order-sensitive binding on identical inputs; compare equal D, equal stored/working bytes and equal task accuracy. For D dense blocks of m-by-m complex matrices, typical naive binding cost O(D m^3), storage O(D m^2), compared with FHRR O(D) on scalar complex components. Flattened similarity is O(D m^2); it can remove matrix-specific inference overhead without converting arbitrary matrix multiplication to pointwise products. Record actual measured end-to-end resource use, no inferred speedup. Original GHRR https://arxiv.org/abs/2405.09689; Nov 12 2026 acceleration https://arxiv.org/abs/2611.16363 and DATE 2026 https://ieeexplore.ieee.org/abstract/document/11539261. Exact historical Claude assessment of GHRR not recovered; architecture choice reflects owner's recollection and independently supported complexity reasoning.

## Software/hardware co-design

- First establish faithful scalar/vector mathematical oracles, common typed operation descriptions and fused CPU implementations. Measure complete pipelines, not just final vector bytes or isolated binding loops. Optimizations: bitpacking, SIMD/popcount, fused bind/bundle/compare, fixed/quantized phase with accuracy controls, FFT convolution, BLAS matrix kernels, streaming counters, resident codebooks and batching. No silent approximation of exact references. Compare single and bounded multithreaded CPU, tuned conventional algorithms, and optional GPU only when relevant, retaining transformer resource reservation.
- Define a backend-neutral bounded command/operand/result protocol and memory placement/lifetime semantics before hardware selection; keep large codebooks, accumulators and intermediate states resident where practical. Quantify dispatch, DMA transfer and synchronization, kernel, cleanup/readback, independent verification, index build/update, and host orchestration separately. Compare cold and warm p50/p95 latency, throughput, full RAM/VRAM/board memory, sustained power/energy when actually measured, and accuracy. Small query transfer overhead may overwhelm acceleration. Identify break-even batch and working-set sizes and concurrent-transformer impact, compare against optimized exact graph/hash/SQLite FTS5, vector nearest-neighbor, HDC software and task-specific conventional ML, without deliberately weak baselines. Include common matched information contracts, update/restart behavior and precision.
- FPGA readiness joins COG-03F software co-design (operation IR, reference kernels, golden vectors, synthesis/simulation eligibility and measured CPU profiles) while physical PCIe FPGA acquisition, driver, bitstream, DMA custody, synthesis and on-board measurement remain COG-09. Research existing accelerator implementations as leads: generalized AXI accelerator https://www.mdpi.com/2079-9292/15/2/489 and primitive-driven FPGA inference https://arxiv.org/abs/2601.20061. Do not extrapolate a particular published benchmark to this engine. Hardware choice depends on demonstrated workload, board memory/bandwidth, PCIe topology, development tools/licensing, host OS driver support and measured transfer budget; no card recommendation or purchase yet.
- Prioritize tasks in which HDC's distributed representations may be useful: structured role-aware composition, noisy partial cues, associative factorization, streaming/continual learning, temporal/graph reasoning and simultaneous queries. Exact lexical search and clean canonical retrieval remain strong controls rather than mandatory target replacements. Accuracy, resource usage, and actual task results define tradeoffs. A coherent architecture may lose to all baselines in a task; document that rather than lower acceptance criteria.
- COG-03G includes genuine integrated pipeline ablations: same encoder/input and witness checks, separate static vs adaptive encoding, FHRR vs optional GHRR, memory and cleanup variants, optimized vs reference execution. Test real end-to-end pipeline cost and failure behavior rather than concatenate independent kernel wins. COG-08 actual low-resource hardware, COG-09 FPGA, COG-10 fixed-model efficacy, COG-11 Lu protected host remain distinct. No production route until appropriate acceptance and owner approval.
