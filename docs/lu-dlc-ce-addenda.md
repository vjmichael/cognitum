## Boundary and terminology

**Cognitum is developed and tested independently as an optional, separately installable and distributable Lu-native DLC Core Extension (CE).** A **CE** provides reusable capabilities/tools to the Lu host and its loaded transformer; it is not an MCP server, a mandatory Lu base-core feature, a replacement model/agent loop, or a DLC Workspace. A **DLC Workspace** is a specialized, full application environment/UI (e.g. IDE or Film Studio) that can consume CEs and Lu services. Vanilla Lu remains available. Cognitum components (C01–C19) may be enabled independently within a CE distribution, subject to Lu authority; they are not nineteen automatically advertised model tools.

**Project rule:** We may inspect Lu to discover compatibility issues. We **never edit, commit, push, build, install, clean, reset, or otherwise modify Lu** from Cognitum work. Every requested Lu change goes here as a scoped addendum with status **proposed** until the independent Lu effort explicitly accepts it. The separate Lu effort owns architecture choice, implementation and release gates. Changes made only in Cognitum are tracked as Cognitum work, not Lu addenda.

**Loaded transformer rule:** Lu controls provider/model selection, agent orchestration, tools, permissions, sessions and user-facing results. Cognitum exposes strictly bounded, evidence-bearing operations through approved Lu-native CE contracts. Improvement is assessed on Lu + selected transformer vs Lu alone and Lu + competent standard tools; no claim of changes to model weights.

## LU-CE-007: typed result translation proposal (Cognitum implementation underway)

[Cognitum typed capability result v1 — implemented contract](components/core-runtime/P1-P2-typed-results.md) and [merged PR #3](https://github.com/vjmichael/cognitum/pull/3) define an **opt-in Cognitum Python result contract** covering canonical exact rational, explicitly uncertain decimal estimate, snapshot-matched retrieval references, dry-run-only, and sanitized failure categories. Fixed epistemic limitations distinguish **exact formal computation** from **verified user intent**, and candidate references from authority or source truth. This is **not** the adopted Lu Protobuf ABI.

**Read-only host finding:** Lu currently uses `lu.v1.ToolReply.oneof outcome` (either `output` typed bytes or `failure` `ToolError`), and validates model-visible JSON through its `ModelToolCodec`. Proposed translation for Lu team:
1. `completed` with a validated domain value → **dedicated generated Protobuf output**; preserve value kind, evidence reference, limitations and assurance derived by Lu-reviewed codec.
2. `denied` / `invalid_input` / `unavailable` / `timed_out` / `error` → Lu's **native failure arm**, with sanitized `code` and reviewed `retryable` flag; never wrap a failed execution as successful `output`.
3. `validated` (dry run) → host-approved representation explicitly conveying that no execution occurred; not an ordinary exact/approximate success.
4. **Unknown status, outcome schema, evidence/limitation code or newer major version → reject**, never silently coerce to “ok” or parse from a generic JSON blob.
5. Lu must continue to derive authenticated subject/workspace scopes from its trusted host, not Cognitum's candidate IDs or model-generated metadata.

**Cognitum verification:** [PR CI 40445966151](https://github.com/vjmichael/cognitum/actions/runs/40445966151) passed **76 unit tests and 12 synthetic replay cases per job** on Windows/Linux Python 3.11/3.13. This tests only Cognitum's contract and trusted Python calculator adapter, not Lu's actual model or worker.

The Lu team determines the final `.proto` package, `optional` presence semantics, ABI version policy, status-to-transport mapping and model-visible codec. This proposal **does not request replacing Lu's host core or editing `lu.v1.ToolReply` when its existing typed-oneof design suffices**. Status remains **Proposed** pending separate Lu authority and compatibility tests.

## LU-CE-003 / LU-CE-007 — mandatory Protobuf-native integration correction (2026-10-26)

**User-confirmed requirement:** Cognitum's Lu-facing native tool input and success-output messages **must be real generated/descriptor-backed Protobuf wire payloads**, not a JSON-only or ad hoc custom IPC replacement. Use Lu's existing `lu.v1.ToolCall` / `lu.v1.ToolReply.oneof outcome`, `ProtoPayload` exact type URLs, `NativeToolRegistry` and `ModelToolCodec`. Model-visible JSON is Lu's external adapter edge; Cognitum's internal/native domain wire is Protobuf.

**Cognitum-only implementation in review:** [native Protobuf work branch](https://github.com/vjmichael/cognitum/tree/cognitum/c01-protobuf-native-messages) defines [`cognitum.v1` tool messages](https://github.com/vjmichael/cognitum/blob/cognitum/c01-protobuf-native-messages/proto/cognitum/v1/capability.proto) and a [bounded Python protobuf codec](https://github.com/vjmichael/cognitum/blob/cognitum/c01-protobuf-native-messages/cognitum/protobuf_codec.py). It includes binary round-trips, `proto3 optional` presence checks, source/binding compile-shape CI and exact success-vs-failure mapping. **This branch does not register/install a Lu tool, send a Lu ToolCall, or modify Lu.** CI evidence must be checked against its final head before promotion.

**Requests to separate Lu team (still all Proposed):**
- Approve how separately installed `cognitum.v1` message files and versions become visible to Lu's Rust protobuf build without creating a second host RPC envelope; check `proto3 optional`, reserved numbers, `type.googleapis.com/cognitum.v1.*`, message identity and backward compatibility.
- Map the approved Cognitum native operation success to Lu's Protobuf `ToolReply.output` with its exact registered output type URL. Map denial/unavailable/timeout/error to Lu's `ToolReply.failure` using Lu's own `ToolError` type; no serialized failure hidden inside successful output.
- Preserve Lu's host-authenticated session/permissions and model-facing JSON codec. This is **not** permission to edit `vjmichael/jan_alt` from Cognitum.

The initial `CapabilityResult` JSON/datataclass contract is still useful for standalone evaluation, API/debugging and legacy conversion, **but it is not the native Lu integration format**. An approved Lu-provided Rust bridge, OS worker and feature gate remain separate C02/C04 work.

## LU-CE-006 — C02 typed worker protocol evidence (2026-10-26)

Cognitum now contains an **inert, versioned native worker wire proposal** at [`proto/cognitum/worker/v1/worker.proto`](../proto/cognitum/worker/v1/worker.proto) with [`worker_wire.py`](../cognitum/worker_wire.py). It uses Protobuf exclusively between proposed host/worker endpoints and a strict `oneof` success/failure envelope, matching the requirement that native Lu IPC **never uses JSON or untrusted pickle**. It includes no grant, caller-identity, sandbox or permission field, because Lu must derive those from trusted host authority **out of band**. The source/binding shape is compiler-checked on Windows/Linux CI and malformed messages fail closed; review [C02 P1/P2 notes](components/security/P1-P2-protobuf-worker-boundary.md).

**Blocked host tasks (LU-CE-006 remains Proposed):** authenticated capability/session broker, genuine Windows AppContainer/LPAC or equivalent restriction, handle/network/file denial, Job Object process tree and quotas, bounded framed and authenticated IPC channel, cancellation/drain/revocation tests, and negative OS-level penetration cases. A valid Protobuf frame is **not** an OS isolation attestation. `worker_wire.start_isolated_worker()` is intentionally disabled and **always rejects**. The legacy trusted-only `worker.py` still uses multiprocessing pickle and must not be an execution path for untrusted CEs.

## LU-CE-006 — Host supervisor negative acceptance contract (Cognitum-only)

**Implemented only in Cognitum:** [`cognitum.security.v1.SupervisorAcceptancePlan`](../proto/cognitum/security/v1/supervisor_acceptance.proto) is a **binary Protobuf test specification**, with explicit deny/reap/resource-enforcement requirements for identity, permission scope, process-tree breakup, filesystem, network, handles, quotas, cancel/revoke/unload, stale replies and secret-safe auditing. [C02 report](components/security/P1-P2-supervisor-acceptance.md) documents the host acceptance matrix. Source Protobuf fields, enums and reserved ranges are CI-checked; [CI 40454579833](https://github.com/vjmichael/cognitum/actions/runs/40454579833) passed 147 unit tests, 12 replay cases and four Protobuf schema comparisons on Linux/Windows Python 3.11/3.13.

**Separate Lu team action remains Proposed:** build the actual trusted OS supervisor and independent negative-test harness, then report real worker process/network/handle/file/CPU/RAM restrictions, descendant reaping, revocation/late-output races, platform versions and logged evidence. A Cognitum synthetic test sequence or matching Protobuf bytes do **not** authenticate the host or prove OS isolation. `start_isolated_worker()` **remains unconditionally blocked**. Do not set any production CE permission or launch flag from this plan.

## LU-CE-006 — Signed host-conformance evidence proposal (C02 gate)

**New Cognitum-only artifact:** the [binary Protobuf signed host runner receipt](../proto/cognitum/security/v1/supervisor_acceptance.proto) is checked by [`supervisor_conformance.py`](../cognitum/supervisor_conformance.py) using **a public key, nonce, host/worker build hashes, OS platform and runner identity supplied independently by Lu's trusted host**. The verifier enforces domain-separated Ed25519 signatures, freshness, full relevant-probe coverage, nonzero evidence digests and fail-closed replay-across-challenge/version/payload handling. The signed receipt is **a host claim**, not an independently verified sandbox or automatic authorization. [C02 gate report](components/security/P2-host-conformance-gate.md) and [CI 40455875310](https://github.com/vjmichael/cognitum/actions/runs/40455875310) cover 162 unit tests, 12 replay and four Proto compiler comparisons per Windows/Linux/Python job. Ephemeral CI signing keys cannot confer Lu authority.

**Remaining Lu-only security work remains Proposed, not approved:** a real native OS-isolated supervisor, restricted file/network/handle/process tree and quotas, host runner key provisioning/custody, one-use nonce consumption and independently executed negative probes with securely retained OS measurements. The worker start gate is **still hard-denied**, even with a well-signed receipt. This Cognitum effort cannot and will not edit Lu.
