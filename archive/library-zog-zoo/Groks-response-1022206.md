>Yes — your engineering decision is sound and aligns with where the field is heading. HDC (and to a lesser extent KAN) maps extremely well to FPGA and emerging ASIC / compute-in-memory substrates. The core operations (XOR/bind, majority/bundle, cyclic shift/permute, Hamming/popcount similarity) are bit-parallel, low-precision, and highly regular, so they love custom datapaths far more than they love a general-purpose GPU’s floating-point matrix engines.Hardware landscape (2025–2026)FPGA is currently the sweet spot for independent researchers:
Multiple open and published accelerators exist (AXI-HDC on Zynq, nano_hamming single-cycle Hamming kernels, RouteHD class-parallel designs on Alveo U200, HyperX / NysX for graph HDC, patch-based image HDC on Alveo U280, etc.).
Typical numbers vs optimized GPU baselines: 4–60× lower latency and 100–300× better energy per inference on edge-scale workloads. Routing congestion (not logic) is often the real limit when you go very wide (high class parallelism or very large D).
You can keep the exact same high-level algorithm (your Python/NumPy or C++ reference) and re-implement only the hot primitives in HLS / Verilog / VHDL. That makes a clean FPGA-vs-GPU bake-off straightforward.
ASIC / specialized silicon:
Yes, custom silicon exists and is accelerating. Examples include 40 nm few-shot HDC chips, SOT-MRAM / FeFET compute-in-memory arrays that do bind + search in-memory, digital HDBinaryCore-style programmable processors, and photonic / electro-photonic prototypes.
Most are research or low-volume; none are commodity “drop-in HDC ASICs” you can buy today. The practical path for you is still FPGA first, then tape-out or partner if the numbers look compelling.
Emerging non-volatile memories (FeFET, RRAM, SOT-MRAM) are particularly interesting because bundling and associative search can be done with almost zero data movement.
KAN on hardware:
KAN’s univariate spline edges map naturally to lookup tables. KANELÉ (2025–2026) is the current standout FPGA flow: co-optimized quantization + pruning → pure LUT evaluation, up to ~2700× latency reduction vs prior KAN-on-FPGA work, and competitive with other LUT-based networks, especially on symbolic / formula-like tasks. There is also analog compute-in-memory work for larger KANs.
So your “CPU/FPGA/ASIC first” priority is even stronger for KAN than for a dense MLP.
GPU is still useful for rapid algorithmic exploration and for the transformer backbone, but once the HDC/KAN pieces stabilize, moving the critical path off-GPU is the right long-term efficiency move — especially under your solar power budget.New / boundary-pushing HDC techniques worth incorporatingYour current harness already has solid baselines (MAP-style, Random Indexing, n-grams, FHRR variants, binary shortlist + float rescore, equal-memory points). Here are higher-leverage directions that are still research-grade and map well to custom hardware:
Dynamic / adaptive hypervector generation
Low-discrepancy sequences or single-source generators that produce near-orthogonal vectors on-the-fly (no big static codebook). Recent ID-VSA / DystoHD-style work shows large memory savings and better scaling when D or vocabulary size changes.
Resonator networks + iterative cleanup
Beyond simple one-shot unbinding. Resonators can factor superpositions and recover clean factors under heavier interference — exactly the regime where your H2 showed weaknesses (superposed A for XOR, noisy unbind for CONV). Hardware-friendly iterative versions exist.
Nyström / kernel approximations inside HDC
Especially useful if you ever want graph or structured data (HyperX/NysX line of work). Landmark selection with DPP (determinantal point processes) + streaming projection is already FPGA-proven and improves accuracy while staying energy-efficient.
Gaussian Polygon / multiscale interpolation in HV space
Lets the model adapt to different feature scales without full retraining. Good accuracy gains on image and remote-sensing data; the operations stay simple enough for FPGA.
Structured / entity-attribute-value encodings + ego-binding
For multi-agent or modular AI use-cases (your hybrid vision). Explicitly separates transmission fidelity from conversion fidelity and uses receiver-centric binding. Pushes HDC toward higher semantic fidelity rather than pure bag-of-features.
Non-uniform error protection / fault-aware design
Since you are targeting FPGA/ASIC, build in region-wise ECC or Hamming-weight-based sensitivity analysis from day one. HDC is naturally noise-tolerant; making that explicit in the hardware is a differentiator.
Hybrid neural-HDC with in-memory compute
FeFET / RRAM arrays that do both neural feature extraction and HDC reasoning on the same fabric (UnO-NeSy style). This is the longer-term “push the boundary” play if you ever get access to a university or foundry collaboration.
Practical recommendation for your project
Keep the custom NumPy / pure-Python reference as the golden model (exactly as you are doing).
Add a thin, hardware-oriented C++ or HLS-friendly layer that implements only the primitives (bind, bundle, permute, Hamming, resonator step).
Port that layer to an accessible FPGA (Zynq UltraScale+ or Alveo if you can get cloud access; even a cheap Zynq board is enough for micro-benchmarks).
Run the identical algorithm on GPU (your current R9700 via ROCm) vs FPGA and publish the latency / energy / accuracy delta. That comparison itself is publishable and strengthens the modular claim.
For the boundary-pushing part, pick one or two of the techniques above (resonator cleanup + dynamic HV generation are the highest ROI for your symbolic-routing use-case) and add them as optional pipelines in the existing harness. Measure them under the same multi-seed, multi-noise, real-data protocol you already locked.
You do not need to chase every new paper. The combination of (1) a clean, reproducible software golden model, (2) FPGA-first implementation of the hot path, and (3) one or two non-standard techniques that actually help the modular hybrid (symbolic state + routing) will already put you ahead of most academic HDC work that stays purely in software or only optimizes classification accuracy.If you tell me which FPGA board (or cloud access) you can realistically get, or which of the new techniques looks most interesting for the VR / modular AI angle, I can help sketch the concrete next experiments or the hardware interface layer.
